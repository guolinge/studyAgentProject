# 个人学习型知识 Agent —— 设计文档

> 状态:设计定稿,待评审
> 日期:2026-07-31
> 形态:独立 agent 应用(TypeScript + Claude Agent SDK / Claude API,自托管 loop)

---

## 一、背景与目标

### 1.1 使用者

前端开发工程师(了解后端),热爱学习计算机各领域知识,目标成为资深技术人员 / 架构师 / 行业专家。日常通过公司 AI 中台(ai.futuoa.com)问答学习,并把问答链手动粘贴、整理到飞书文档积累知识。

### 1.2 要解决的四个痛点(源自 `instructions/需求.md`)

1. **答案风格不合口味**:例子幼稚(厨房/学霸/银行/排队之类),缺 JS/TS 代码或代码无注释,缺"从 0 到 1"的推导过程,缺图。
2. **飞书分类混乱**:大量重复文件夹(如「每日任务」里 5 个「数据库专题」)、命名不准、粒度不一,复习时找不到。
3. **内容僵硬**:想在旧文档的某个锚点嵌入新内容,中台只能生成新回答,做不到。
4. **重复研究**:已经记录过的知识又从零再问一遍,制造重复文档。

### 1.3 中台的根本局限

中台只能"针对单一问题、生成单一新回答";既不能按使用者风格作答,也不能调外部工具查已有知识库,更不能回头修改旧文档。本 agent 的本质,是把「问 · 存 · 改」重新缝合成一个闭环。

### 1.4 项目的双重目标

- **产出**:一个真正好用的个人知识 agent。
- **过程**:使用者希望**亲手体验开发 agent 的全过程**(成为技术专家的路径之一)。因此选择"自己托管 agent loop"的形态,而非把 loop 托管给平台。

## 二、核心决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 形态 | **Claude API + tool use,自托管 loop** | 亲手写编排/门/工具 = 真正的"开发 agent"体验;Managed Agents 会把 loop 托管掉,且其沙箱用不了本地已登录的 `lark-cli` |
| 语言 | **TypeScript**(`@anthropic-ai/sdk`) | 匹配使用者前端背景与 JS/TS 偏好 |
| 中台定位 | **合规兜底**,不进入本系统主流程 | 通用技术知识(占知识库 90%+)在本 agent 内处理即可且更优;真正涉及公司机密时才用中台 |
| v1 前端 | **命令行 / 终端驱动** | 先把流水线和答案质量跑通、调准;网页 UI 放第二步 |
| 一切可调项 | **配置文件化**(模型参数 + prompt/rules) | 使用者会频繁微调,改文件不改代码 |

### 2.1 速度约束(第一优先级)

速度是使用者最痛的点。真实 agent 必须**预置掉一次性开销**(工具学习、渲染踩坑、分类重扫),目标单次几分钟级。使用者接受"为惊艳略慢",但**绝不接受 30 分钟级**。设计上以此为硬约束:搜索结果在流水线内传递(不重复搜)、执行/审核用轻量模型、文字先出图后补。

## 三、"惊艳"答案规范(个性化核心)

单篇答案在模型层面很难碾压中台;差异化靠**可打磨的维度**。使用者明确选定三个惊艳维度(将固化为 `style-rules.md` 的硬规则):

1. **推导深度 + 被否决的替代方案**:从第一性原理讲透"为什么这么设计",包含"why not X"(否决了哪些更直觉的路、为什么),而非只讲"它是什么"。
2. **跨界心智模型 / 类比**:把新概念连到使用者已知的东西(例:pnpm 的 CAS ≡ git object store,同一个内容寻址思想),给"一下就通"的心智模型。
3. **手绘级 SVG 图**:抛弃呆板的 mermaid 方框,用有视觉层级、有设计感的定制 SVG(也支持 mermaid,按图类型选)。

**明确不看重**:"工程实战 / 真实坑 / 生产事故"这一维度使用者未选——要的是"通透 + 好看",不是战场故事。

**其他硬偏好**:拒绝幼稚生活化比喻;代码用 JS/TS/伪代码且带注释;标注主流 vs 过时;不啰嗦。

### 3.1 表达形式菜单("叶子/果实")

「内容组织 agent」为每个小节从下列菜单中挑选表达形式 + 估算体量。这是个性化落地的关键决策层。

| 表达形式 | 说明 | 对应惊艳维度 |
|---|---|---|
| 文字解释 | 叙述性讲解,打底 | 基础 |
| 从 0 到 1 推导 / why-not-X | 讲透为什么这么设计、否决了哪些路 | ⭐维度 1 |
| 跨界类比 / 心智模型 | 连到已知的东西(如 CAS≡git object) | ⭐维度 2 |
| 图解 | 架构/流程/时序/数据流/关系图,mermaid 或手绘 SVG | ⭐维度 3 |
| 代码示例 | JS/TS/伪代码 + 注释,带复杂度档位 | 硬偏好 |
| 对比表格 | vs 竞品/旧方案,讲 trade-off | — |
| 一句话结论 | callout 收尾金句 | — |
| 可追问的钩子 | "想更深可往 X/Y/Z 挖" | — |

## 四、架构:6 个 agent + 编排器

```
[输入: 简短问题 / 问题+答案 / 链接]
        │
        ▼
┌───────────────── 编排器(orchestrator,你的 TS 代码)─────────────────┐
│  手动 loop(非 tool runner)—— 因为两道人工门需要停下来等使用者        │
│                                                                      │
│  ① 问题分析 agent ── 查飞书是否已有 → 搜索+思考 → 出【一级大纲+意图】    │
│        │  ←── 🚪门1(轻):确认范围/意图,3 秒扫过                        │
│  ② 内容组织 agent ── 细化到三级 + 每节定"表达形式+体量"(复用①搜索结果) │
│        │  ←── 🚪门2(重):确认骨架,反复迭代到通过                       │
│  ③ 内容生成 agent ── 生成正文 + 画图指令(复用①②搜索,按需补搜)         │
│        │                                                              │
│  ④ 内容审核 agent ── 对照骨架做轻量检查清单 → 定归档位置                 │
│        │              (不达标→打回③;达标→交⑤)                        │
│  ⑤ 飞书文档 agent ── 先写文字(最快呈现)→ 图和耗时项后台慢慢补           │
│                                                                      │
│  ⑥ 沉淀 agent(Distiller)── 复盘本次反馈 → 蒸馏规则 → 🚪你批准 →        │
│        写回 prompts/*.md + git commit(每条经验可回溯、可回滚)          │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.1 各 agent 职责

| Agent | 类型 | 职责 | 落地方式 |
|---|---|---|---|
| **问题分析** | 生成型 | 明确意图、查重(调飞书 agent 查已有文档)、搜索+思考、出一级大纲 | `messages.create()` + 该角色 system prompt |
| **内容组织** | 生成型 | 细化到三级大纲、为每节定表达形式+体量 | 同上 |
| **内容生成** | 生成型 | 生成正文 + 画图指令(不亲自画) | 同上 |
| **内容审核** | 校验型 | 对照骨架跑检查清单、定归档位置 | 同上(轻量模型) |
| **飞书文档** | 执行型 | 查/增/改/删飞书(内容它不生成,只执行);画图 | tool 函数 → `child_process` 调 `lark-cli` |
| **沉淀(Distiller)** | 进化型 | 从反馈蒸馏规则、提议、写回 prompts 文件 | `messages.create()` + git 写入(需批准) |

### 4.2 两道门的设计

- **门 1(轻)—— 范围/意图**:只确认"讲哪些一级话题、要不要背景、方向对不对"。故意保持粗(仅一级标题 + 一句意图),使用者秒过。它是个便宜的早期过滤器:范围错了,下游不白费。价值随输入的模糊程度上升(简短明确的问题几乎走过场,链接/"帮我整理"这类模糊输入最需要)。
- **门 2(重)—— 深度/表达形式**:确认三级骨架 + 每节的表达形式与体量。这是使用者花心思的地方,反复迭代到通过。

> 两道门刻意问**不同层面**的问题(范围 vs 深度+表达),避免"确认两遍"的别扭感。

### 4.3 内容审核 = 轻量对照检查,不重读

深度质量已被门1、门2、以及使用者最终亲自阅读三重兜住。审核 agent 只核对"生成是否照批准的骨架执行":每节是否都在?指定表达形式是否用了(该类比的类比了、该画图的给了指令)?代码带注释?有无未解释的晦涩新概念?字数在范围内?不达标打回生成 agent。它是"质检员对图纸验收",不是"重新设计"。

## 五、沉淀 Agent(Distiller)—— 自进化机制

skill 不该一成不变。Distiller 把使用者一次次的反馈,沉淀成规则,写回 `prompts/` 文件,让系统越用越懂使用者。

**观察信号**:门1/门2 的反馈原话("这个类比不好""太长了""想要更多代码")、使用者对大纲/骨架的修改(提议 vs 改成的,差异即信号)、被砍掉的表达形式、成稿上的评论。

**进化流程(关键安全设计)**:

```
一次文档完成后
  → Distiller 复盘本次反馈
  → 蒸馏候选规则(例:"3 次拒绝生活化类比、2 次要 git 类比 → 建议加规则:
     类比只用已知技术(git/http…),禁止生活化比喻")
  → 🚪 展示这条 diff,使用者批准
  → 才写回 style-rules.md(或对应角色 prompt),并 git commit
```

**为什么必须"提议→批准→写回",不能静默改**:自动改写规则会学错(把偶然反馈当永久偏好),久了规则漂移。加这道门 + git 记录后,每条进化都可审、可回滚。写回目标以 `style-rules.md` 为主;若经验是角色特定的,则写对应角色 prompt。

## 六、配置与文件设计

一切频繁微调项都文件化,改文件不动代码。

### 6.1 模型参数配置 `agents.config.json`

`defaults` 打底,每个角色覆盖:

```json
{
  "defaults": { "model": "claude-opus-4-8", "effort": "high", "maxTokens": 16000, "thinking": "adaptive" },
  "agents": {
    "questionAnalysis":     { "effort": "medium" },
    "contentOrganization":  { "effort": "high" },
    "contentGeneration":    { "effort": "high", "maxTokens": 32000 },
    "contentReview":        { "model": "claude-haiku-4-5", "effort": "low" },
    "distiller":            { "effort": "medium" }
  }
}
```

- 每个角色 = `defaults` 合并自身覆盖项。改哪个角色用什么模型/effort/预算,只动这一个文件。
- 启动时读取(v1 重启生效;以后可加热重载)。
- 用 TS 类型/schema 校验,避免写错模型 ID。
- 可编辑字段:`model`、`effort`(low/medium/high/xhigh/max)、`maxTokens`、`thinking`;以后可扩展 `streaming` 等。

### 6.2 prompt / rules 文件

```
prompts/
├── style-rules.md          ← 惊艳规则/偏好(单一真相源,被组织+生成引用;Distiller 主要写这里)
├── question-analysis.md    ← 问题分析角色 prompt
├── content-organization.md ← 内容组织角色 prompt(含表达形式菜单)
├── content-generation.md   ← 内容生成角色 prompt
├── content-review.md       ← 审核角色 prompt(含检查清单)
└── drawing-rules.md        ← 作图规范(含飞书画图的坑,见附录 A)
```

运行时读取。**全部纳入 git**——这是 Distiller "可回溯、可回滚"的前提。

### 6.3 建议目录结构(v1)

```
studyAgentProject/
├── agents.config.json          # 模型参数配置
├── prompts/                    # 角色 prompt + 规则(git 跟踪)
├── src/
│   ├── orchestrator.ts         # 编排器:手动 loop + 两道门
│   ├── agents/                 # 各角色的 messages.create 封装
│   ├── tools/
│   │   └── lark.ts             # 飞书 agent:child_process 调 lark-cli
│   ├── config.ts               # 读取+校验 agents.config.json
│   └── distiller.ts            # 沉淀 agent:蒸馏+提议+写回+commit
├── docs/                       # 设计文档等
└── instructions/               # 需求与素材
```

## 七、关键落地细节

### 7.1 SDK 与模型参数(已核对当前用法)

- 包:`@anthropic-ai/sdk`,`import Anthropic from "@anthropic-ai/sdk"`。
- 每个生成型 agent = 一次带专属 system prompt 的 `client.messages.create()`。
- 两道门 = 手动 loop 里的暂停(官方文档明确:需要 human-in-the-loop 审批时用手动 loop,不用 tool runner)。
- 模型默认 `claude-opus-4-8`,`thinking: { type: "adaptive" }`,`output_config: { effort }`(由配置文件驱动)。
- 长输出走 streaming(`.stream()` + `.finalMessage()`),避免 SDK HTTP 超时。

### 7.2 搜索结果在流水线内传递(省速度/省 token)

联网搜索只在必要处做一次,结果作为上下文顺流水线往下传(拼进后续 agent 的入参),后续 agent 觉得不够再按需补搜。避免"每个 agent 各搜一遍"。

### 7.3 飞书集成:复用现成 lark-cli

飞书文档 agent 的 tool 函数通过 Node `child_process` 调用使用者本地已登录的 `lark-cli`——复用现有授权、画图能力与踩坑经验,不重造飞书对接层。能力:搜索文档、读目录结构、读文档大纲、写内容、块级修改/迁移、删除、画图。

## 十、待确认 / 风险

- **飞书画图渲染坑**(见附录 A)需固化进 `drawing-rules.md`,否则每次重踩(那是首次演示 30 分钟里的主要开销)。
- 速度:即便预置掉一次性开销,tool 往返 + 多步验证仍比中台的纯文字流式慢,现实目标 1~5 分钟。若门太多导致操作累,后续再评估"简单问题走快车道"的分级(当前决定:先不分级、全走)。
- 搜索来源偏英文/全球(底层美区搜索),对通用技术知识多半是优势;查"中国特供"内容时可能不如国内搜索。

## 附录 A:飞书写图的已知坑(实测 2026-07-30)

1. `<whiteboard type="mermaid" path="@file.mmd">` 的 `path` 引用**不生效**(报 `degrade_code=5002`),必须**内联** mermaid 内容。
2. 飞书 mermaid 渲染器**拒绝特殊字符**:节点/边标签里的 `@`、`~/`、`()`、内层引号、emoji 会导致 `degrade_code=2107` 整块被丢弃。须**清洁化**标签(如 `foo@1.0.0` 写成 `foo 1.0.0`)。最小 mermaid(`graph TD; A-->B`)能渲染,可用来隔离问题。
3. SVG 画板(`<whiteboard type="svg">`):须完整自包含(含 `<svg>` 根 + `viewBox`);**不支持** `radialGradient`/`filter`/`clipPath`/`mask`/`pattern`;箭头用 `<polygon>` 手绘;文字必须用 `<text>`。
