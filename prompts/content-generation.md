- **开篇用问题场景切入**:禁止"X 是……"的定义式开头。先摆出一个读者会遇到的真实问题,让人产生"对,这确实烦"的共鸣,再引出概念。

### 2.2 关键一步:每次触发都重置定时器

上一版的问题出在:每次 `keyup` 都**新起**一个定时器,却没人取消旧的。敲 5 个字符就有 5 个定时器排队,300ms 后挨个引爆——我们想省的请求一个没少。

真正要的语义是"**只认最后一次触发**"。那就让每次新触发**作废掉上一次的等待**:先 `clearTimeout` 掉还没引爆的那个,再重新计时。只要你还在敲,引爆时刻就一直被推后;停手 300ms,最后一个才活到执行。

这和 git 的 `commit --amend` 同构:与其累积一堆中间提交,不如让新动作**覆盖**上一个未定型的状态,最终只留一个。

```js
function debounce(fn, delay) {
  let timer = null;          // 闭包保存"当前在等的那个定时器",跨多次调用共享
  return function (...args) {
    clearTimeout(timer);     // 关键:作废上一次的等待(timer 为 null 时清也安全)
    timer = setTimeout(() => {
      fn.apply(this, args);  // 停手 delay 毫秒后,才真正执行这一次
    }, delay);
  };
}
```

`timer` 必须存在闭包里、而不是每次调用的局部变量——否则后一次调用取消不了前一次的定时器,"塌缩"就无从谈起。这个闭包变量,就是防抖能成立的支点。

### 4.1 why-not 节流 throttle

有人会问:高频事件降频,为什么不用节流?两者的本质区别在于**塌缩的方式**:

| | 防抖 debounce | 节流 throttle |
|---|---|---|
| 触发时机 | 停手后一次 | 固定间隔一次 |
| 连续触发中 | 一直不执行 | 按频率照常执行 |
| 适用 | 搜索联想、resize 结束后重算 | 滚动加载、拖拽实时反馈 |

一句话:**要"最终态"用防抖,要"过程中的采样"用节流**。搜索框要的是你敲完那一下,所以防抖;而滚动进度条要的是过程,所以节流。
